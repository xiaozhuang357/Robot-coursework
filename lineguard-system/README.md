# LineGuard 第一阶段全栈仿真原型

本项目配套《LineGuard 常驻式巡检机器人的软件设计》课程论文：Robot 从 Dock 出发，在单档距模拟线路中移动至指定检测点，采集近距离图像，等待人工复核，然后返回 Dock 并完成锁止、补能确认和数据同步。

首版只验证一条主线，不包含真实电机、单片机、ROS、AI 缺陷识别、复杂越障和商业管理模块。

## 已实现能力

- 完整任务状态机：创建、预检、离站、移动、检测、上传、复核、返航、对接和完成。
- Robot 仿真：位置推进、电量消耗与驻留补能、定点拍摄、返航和安全驻停。
- Dock 仿真：驻留锁止、离站释放、返回对接、充电确认和限次重试。
- 中文管理界面：任务控制台、历史任务、设备状态。
- 实时状态：通过 SSE 自动刷新 Robot 位置、设备状态和任务事件。
- 数据持久化：H2 保存任务与状态历史，本地目录保存模拟检测图像。
- 异常演示：低电量、通信中断、未知障碍、对接失败和模糊图像。
- 指令幂等：同一任务内重复的指令编号不会重复执行，接口返回当前状态并在任务事件中标记为重复指令。该保证由单实例内串行处理加数据库唯一约束共同实现。

## 工程结构

```text
lineguard-system/
├─ backend/                 Java 21 + Spring Boot + H2
│  ├─ src/main/java/        领域状态机、REST、SSE 和设备仿真
│  ├─ src/test/java/        闭环与故障集成测试
│  └─ runtime-data/         运行后生成的数据库与检测图像
├─ frontend/                Vue 3 + TypeScript + Element Plus
│  └─ src/
│     ├─ views/             任务控制台、历史任务、设备状态
│     ├─ stores/            实时数据和任务操作
│     └─ components/        线路视图、状态标签和任务时间线
├─ start-demo.sh             一键构建并启动（macOS / Linux）
├─ stop-demo.sh              停止演示服务（macOS / Linux）
├─ start-demo.ps1            一键构建并启动（Windows）
└─ stop-demo.ps1             停止演示服务（Windows）
```

## 运行环境

- JDK 21

- npm 10+

构建与测试使用 JDK 21。存在多个 JDK 时，以 `mvn -version` 中的 Java 版本为准；在 macOS 上可显式选择：

## 一键启动

macOS 或 Linux：

```bash
./start-demo.sh
```

Windows PowerShell：

```powershell
powershell -ExecutionPolicy Bypass -File .\start-demo.ps1
```

脚本会在后台启动后端和前端，服务就绪后自动打开：

```text
http://localhost:5173
```

结束演示：

```bash
./stop-demo.sh
```

```powershell
powershell -ExecutionPolicy Bypass -File .\stop-demo.ps1
```

运行日志保存在 `.run-logs`，任务数据库和检测图像保存在 `backend/runtime-data`。
两个脚本共用同一份进程记录 `.lineguard-demo.pids.json`，因此不要同时用两种方式启动。

## 推荐演示流程

### 正常闭环

1. 打开“任务控制台”。
2. 选择检测点，点击“创建并开始任务”。
3. 观察 Robot 在线路视图中移动，任务状态自动推进。
4. 系统到达“等待复核”后查看检测图像。
5. 选择人工结论，点击“提交结论并下达返航”。
6. 观察 Robot 返回 Dock，任务进入“任务完成”。
7. 在“历史任务”中检查完整状态时间线和复核档案。

默认仿真周期为 700 ms、每步 120 m，动作时间经过压缩，不能当作真实机器人速度。

### 异常闭环

任务运行时展开“故障演示”即可注入：

- 低电量：自动转入返航；自动返航与人工返航共用同一套联锁，离线、障碍未解除或任务等待人工处理时只压低电量并记录原因，不改任务状态。
- 通信中断：仿真状态转为安全停车并等待人工处理，恢复通信后可人工返航；设备端独立停车仅给出伪代码设计。
- 未知障碍：进入安全驻停，解除障碍后可人工返航。
- Dock 对接失败：返航对接时重试两次，随后安全驻停。
- 模糊图像：下一次图像不可判读，只允许重新采集一次。
- 重复指令：重发同一个派发指令，任务不会重复执行。

演示不同场景前可点击“重置演示环境”。

### 中途终止与召回

任务运行期间点击“终止任务”：

- Robot 尚未离站时，任务直接结束为“任务已终止”。
- Robot 已在线路上时，任务进入“安全驻停”并保留对 Robot 的归属，界面出现“召回返航”按钮。
- 点击“召回返航”后 Robot 沿已验证路线返回 Dock，完成锁止与补能确认，任务按闭环收尾；期间终止与召回两条记录都保留在任务事件中。

这样处理是为了避免为了把机器人撤回来而重复冲击线路：终止动作只改变任务意图，机器人撤离始终走同一条返航流程。

## 核心接口

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/v1/tasks` | 创建任务 |
| `POST` | `/api/v1/tasks/{id}/dispatch` | 预检并派发任务 |
| `GET` | `/api/v1/tasks/{id}` | 查询任务、检测和事件 |
| `POST` | `/api/v1/tasks/{id}/review` | 保存人工结论并返航 |
| `POST` | `/api/v1/tasks/{id}/actions/recapture` | 重新采集一次图像 |
| `POST` | `/api/v1/tasks/{id}/actions/return` | 人工返航 |
| `POST` | `/api/v1/tasks/{id}/actions/abort` | 终止任务 |
| `GET` | `/api/v1/devices` | 查询 Robot 与 Dock |
| `GET` | `/api/v1/events/stream` | SSE 实时事件流 |
| `POST` | `/api/v1/simulator/faults` | 注入或解除仿真故障 |
| `POST` | `/api/v1/simulator/reset` | 重置演示数据 |

失败一律返回 `ProblemDetail`，状态码按原因区分，便于前端与现场排查：

- `400` 请求参数不合法或无法解析；
- `404` 任务、检测记录或检测图像不存在；
- `409` 当前状态不允许该操作——包括命令与任务状态不匹配、检测点已不存在这类数据不一致、并发写入撞上唯一约束；
- `500` 只留给真正的服务内部故障。

「状态不允许」与「数据不一致」都走 409 而不是 500：它们不是后端崩了，把它当内部错误报出来会让排查方向整个跑偏。

## 测试与构建

后端（**必须显式指定 JDK 21**）：

```bash
cd backend
JAVA_HOME=$(/usr/libexec/java_home -v 21) mvn test
```

需要确认 Maven 实际使用的版本，避免在不兼容的 JDK 上运行测试。

前端：

```bash
cd frontend
npm test
npm run build
```

本次实测 64 项自动化测试（后端 32、前端 32）全部通过，覆盖：

- **任务闭环与异常**（后端）：正常闭环的事件子序列、低电量返航、通信中断转人工、未知障碍驻停并在解除前拒绝移动、Dock 对接失败重试后安全驻停、中途终止后召回闭环、驻留中终止、重复指令只迁移一次、仿真推进失败后调度仍能清理。
- **接口契约**（后端）：种子资产与建任务、任务列表逐条解析检测点名称、检测点悬空时返回 409 而不是 500、**列表的 SQL 语句数不随任务数增长**（挂了一个逐条计数的 `StatementInspector`；Hibernate 自带的 `prepareStatementCount` 会把预编译语句复用算成一条，用它断言 N+1 会假通过，所以用例里先校准计数器本身）。
- **重启恢复**（后端）：重启后任务转等待人工、机器人置安全驻停、**坞从瞬时状态归位到等待返回**；已完成的任务与锁止充电中的坞不被改写。
- **检测图像接口**（后端）：取图返回 `image/svg+xml` 且内容确为 SVG（生成那张图的代码曾因格式串问题静默失败）；图像文件缺失时报 404 并带上真实原因，而不是被兜底压成 400"请求参数不合法"；检测记录不存在报 404。
- **SSE 保活**（后端）：心跳按周期给所有订阅发注释行；对端已经关闭的订阅会被就地清理，活着的订阅不被误踢。用例不手动触发心跳，靠调度器自己跑，同时验证"定时在跑"和"不误踢"。
- **SSE 接口契约**（后端）：`/api/v1/events/stream` 以 `text/event-stream` 开流并先发 `connected` 帧；订阅者开着连接时执行一次派发，必须真的收到 `lineguard-update` / `DEVICES_UPDATED` 推送——这是整个实时界面的基础，此前这条路径没有任何用例。
- **二维视图几何**（前端）：检测点与机器人必须落在渲染出来的地线上（解析 SVG 路径反算曲线高度比对）、里程越界夹到杆塔、已行进里程画到机器人处、目标点唯一标记。
- **三维构件表契约**（前端）：字段与构件类型匹配、**轮槽开口朝外**、上下夹持轮关于地线对称且槽底贴线、坞的导向轨对称并让开机体。
- **SSE 增量更新**（前端）：`DEVICES_UPDATED` 与遥测事件直接改状态不回源、非遥测事件回源确认、事件体解析失败兜底、换任务的事件不串写、断流进入重连并按退避重连、**重连后回源补齐断线期间错过的状态变化**（首次接通不重复取数）、刷新页面后重发复用同一指令编号。
- **界面文案不外泄内部命名**（前端）：任务时间线的标题必须显示中文状态名或事件类型的中文名，不能把 `TASK_CREATED`、`TELEMETRY` 这类后端内部命名摆到界面上；未收录的新类型才退回原样，以保证新事件出现时不会显示成空白。

## 后续接入真实设备

后端通过 `DeviceGateway` 隔离任务系统与执行端**的推进**：接口只有 `startOrResume` / `stop` / `stopAll` 三个方法，当前实现把它交给内置仿真调度器。**设备状态是平台侧仿真逻辑算出来直接落库的**，并没有一条真正的设备通信链路——接入 MQTT、串口或硬件网关不是"换个实现"就够，需要新增通信端口（下发与上报）并重新审视"设备即数据库记录"这个假设；任务状态机与数据模型可以保持不动。
